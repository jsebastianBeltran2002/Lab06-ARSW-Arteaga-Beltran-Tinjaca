# BoardEvent Contract — Lab 06

Live collaboration contract between browsers that share a `boardId`. It complements (does not replace) the REST contract in [`api-contract.md`](api-contract.md): REST still creates, loads and snapshots a Board; STOMP carries the interaction events of a live session. See [ADR-003](ADR-003-rest-vs-realtime.md).

## Transport and destinations

| Role | Destination | Direction |
|---|---|---|
| WebSocket handshake | `/ws` | client → server (same origin) |
| Propose a change | `SEND /app/boards/{boardId}/events` | client → `BoardWebSocketController` |
| Accepted changes of a session | `SUBSCRIBE /topic/boards/{boardId}` | server → every client of that board |
| Rejection of *my* event | `SUBSCRIBE /user/queue/errors` | server → the sender only |

Configured in `infrastructure/web/ws/WebSocketConfig` (application prefix `/app`, simple in-memory broker `/topic` + `/queue`, user prefix `/user`), separate from the REST controllers.

## Flow

```text
Client SEND  /app/boards/{boardId}/events
                     |
                     v
BoardWebSocketController   destination boardId == event.boardId ?
                     |
                     v
BoardEventApplicationService   board exists? payload valid for type? transition keeps Board invariants?
                     |                         \
                  accepted                    rejected
                     |                           \
                     v                            v
BROADCAST /topic/boards/{boardId}      /user/queue/errors (sender only, nothing broadcast)
```

The server **validates and applies** an event before broadcasting it. Only accepted events are broadcast, and the accepted transition is already persisted in the `BoardRepository`, so a later `GET /api/boards/{boardId}` returns the same state the live clients see.

## Envelope

```json
{
  "eventId": "f2b2d7c6-5b1e-4a53-9f0e-1c2d3e4f5a6b",
  "boardId": "board-123",
  "type": "ELEMENT_MOVED",
  "actorId": "client-1a2b3c4d",
  "occurredAt": "2026-09-01T12:30:00Z",
  "payload": {
    "element": null,
    "elementId": "rect-1",
    "x": 420.0,
    "y": 180.0
  }
}
```

| Field | Responsibility | Rule |
|---|---|---|
| `eventId` | Unique id of the message. | Required, non-blank. Generated by the client (`crypto.randomUUID()`). |
| `boardId` | Session/board the change belongs to. | Required; must equal the `{boardId}` of the destination. |
| `type` | Semantics of the event. | Required; one of the five types below. |
| `actorId` | Client that originated the interaction. | Required; one per page load (`client-xxxxxxxx`), so two tabs are two actors. |
| `occurredAt` | Instant reported by the sender (ISO-8601 UTC). | Required. Informational only — not used for ordering (see *Deliberately deferred*). |
| `payload` | Minimum data required by the type. | Required; the four keys are always present, unused ones are `null`. |

Envelope rules are enforced by the `BoardEvent` record's constructor; payload rules per type by `BoardEventApplicationService`.

## Event types

| Type | Required payload | Server validation | Effect on the Board |
|---|---|---|---|
| `ELEMENT_CREATED` | `element` | type is `RECTANGLE` or `TEXT`; `id` not already in the board | Adds the element. |
| `CONNECTOR_CREATED` | `element` | type is `CONNECTOR`; `id` new; `sourceId` and `targetId` exist in the board and differ | Adds the connector. |
| `ELEMENT_MOVED` | `elementId`, `x`, `y` | element exists and is not a `CONNECTOR` | Changes only `x`/`y`. Published once, at the end of the drag. |
| `ELEMENT_UPDATED` | `element` | element with that `id` exists; `type` unchanged | Replaces its editable properties (the client uses it for **Edit Text**). |
| `ELEMENT_DELETED` | `elementId` | element exists | Removes it **and every connector whose `sourceId`/`targetId` is that element**. |

`element` has the same shape as in the REST contract (`id`, `type`, `x`, `y`, `width`, `height`, `text`, `sourceId`, `targetId`).

### Examples

```json
{ "type": "ELEMENT_CREATED",   "payload": { "element": { "id": "rect-1", "type": "RECTANGLE", "x": 40, "y": 60, "width": 120, "height": 80, "text": "", "sourceId": null, "targetId": null }, "elementId": null, "x": null, "y": null } }
{ "type": "CONNECTOR_CREATED", "payload": { "element": { "id": "conn-1", "type": "CONNECTOR", "x": 0, "y": 0, "width": 0, "height": 0, "text": "", "sourceId": "rect-1", "targetId": "text-1" }, "elementId": null, "x": null, "y": null } }
{ "type": "ELEMENT_UPDATED",   "payload": { "element": { "id": "text-1", "type": "TEXT", "x": 200, "y": 40, "width": 140, "height": 30, "text": "API Gateway", "sourceId": null, "targetId": null }, "elementId": "text-1", "x": null, "y": null } }
{ "type": "ELEMENT_DELETED",   "payload": { "element": null, "elementId": "rect-1", "x": null, "y": null } }
```

(Envelope fields omitted for brevity.)

## Rejections

A rejected event is **not** broadcast and does not change the Board. The sender receives, on `/user/queue/errors`:

```json
{ "timestamp": "2026-09-01T12:30:01Z", "code": "INVALID_EVENT", "message": "Element not found in board: ghost" }
```

| `code` | When |
|---|---|
| `BOARD_NOT_FOUND` | `boardId` does not exist. |
| `INVALID_EVENT` | Broken envelope, destination/`boardId` mismatch, wrong payload for the type, unknown element, or a transition that would break a Board invariant. |
| `INTERNAL_ERROR` | Anything unexpected (no internal detail is exposed). |

## Client rules

- All STOMP code lives in `js/realtime/board-realtime-client.js`; events are built only by `js/events/board-event.js`.
- The STOMP callback calls `BoardState.applyEvent(event)` and nothing else; the SVG is re-rendered from `BoardState` afterwards. It never touches the DOM directly.
- While live, a client does **not** apply its own change optimistically: it publishes and applies the change when the accepted event comes back on the topic, exactly like every other participant.
- `applyEvent` ignores events whose `boardId` is not the current board, and applying the same creation twice does not duplicate the element.

## Deliberately deferred (Lab #7)

This contract has no sequence number, version or server timestamp. The server applies events in the order it processes them, with a non-atomic read → transition → save over a non-thread-safe in-memory repository. Simultaneous edits can therefore produce lost updates or different arrival orders; Lab #7 uses exactly this path to motivate a consistency strategy.
